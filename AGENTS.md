# Правила работы с приложением

Эти правила работают самостоятельно, без истории чата и доступа к мета-проекту. Изменения исходного шаблона не применяются автоматически.

## Перед началом

1. Проверь `git status --short --branch`, текущую ветку, upstream и remote. Получи изменения через `git fetch origin` при настроенном remote.
2. Безопасно обнови рабочую ветку; при чистом дереве и настроенном upstream используй `git pull --ff-only`. При расхождении или локальных изменениях сначала сохрани и разбери работу; не применяй разрушительный сброс, force push и удаление чужих изменений.
3. Прочитай README, REQUESTS, SPEC, BACKLOG и последние CHANGELOG/RUNLOG. Выбери задачу и отметь её «В работе».

## Запросы и требования

Записывай значимые сообщения пользователя в REQUESTS с датой и устойчивым REQ-ID. Сохраняй доступную исходную формулировку; пересказ помечай явно. Старые записи не переписывай: уточнения и отмены добавляй новыми записями со ссылками на предыдущие. Не сохраняй весь чат и секреты. Инициативы агента не выдавай за пользовательские требования.

SPEC описывает согласованное целевое поведение со ссылками на запросы, а не перечень уже реализованного. При изменении договорённостей обнови спецификацию. Для мелкой правки без изменения поведения обновлять её не нужно. Неоднозначности фиксируй в открытых вопросах.

## Бэклог

Задачи имеют устойчивые TASK-ID, источник (ссылка на REQ либо «инициатива агента») и критерий завершения. Используй статусы «В очереди», «В работе», «Заблокировано». Для блокировки укажи причину и нужный следующий шаг; для частичного выполнения — что осталось.

Завершённое перенеси в CHANGELOG и убери из активного бэклога. Отменённое сохрани в разделе отмен со ссылкой на запрос об отмене. Не переиспользуй идентификаторы.

## Реализация и проверка

Пользуйся командами из README. Пока команды, стек и ограничения не определены, не выдавай шаблон за рабочее приложение: сначала установи фактические условия и обнови инструкции. Проверяй соразмерно изменению; не утверждай, что запуск или поведение проверены, если была только сборка.

В RUNLOG фиксируй значимые проверки и передачи между устройствами: дату, устройство/ОС, версию, команду/сценарий, результат и непроверенное. Для незакоммиченных изменений укажи базовый коммит и наличие локальных изменений; если коммитов ещё нет, явно запиши это. Не сохраняй полные технические логи по умолчанию.

После содержательного этапа добавь CHANGELOG: дата, ссылки на REQ/TASK, что изменено, что проверено, ограничения. Частичный результат не называй завершённым.

## Запуск и мета-проект

Поддерживай подробный запуск для macOS и Windows в README. Неподдерживаемые и непроверенные платформы помечай явно. При изменении команд, зависимостей или платформ обнови также краткую инструкцию в карточке мета-проекта (её URL должен быть в README). Если мета-проект недоступен, добавь задачу в BACKLOG и сообщи, что карточка не обновлена.

Не дублируй спецификацию и бэклог в мета-проекте. Код приложения остаётся в собственном репозитории, вне мета-проекта.

## Завершение и передача работы

Обнови необходимые документы, выполни подходящие проверки, просмотри diff и staged diff, сделай осмысленный коммит и push. Если remote отсутствует или push не выполнен, сообщи об этом явно. Не выдумывай адрес remote.

Для передачи незавершённой работы используй отдельную ветку, отправь её и оставь в BACKLOG заметку: сделано, осталось, ветка, следующий шаг. На другом устройстве продолжай по документам. При одновременной работе используй разные ветки. Git не переносит контекст чата и не запускает агента на другом компьютере.

Не коммить абсолютные локальные пути, секреты, .env с секретами, приватные ключи, зависимости, кэши, временные файлы и локальные пользовательские данные. Пути устройств хранятся в local.yaml мета-проекта, исключённом из Git. Общие ссылки — относительные внутри репозитория или URL между репозиториями.

## Особенности проекта

Один репозиторий, два клиента: `ics-monitor` (Python, локальный HTTP-сервер) и `android-calendar` (Java 17, Android SDK 35, Gradle 8.9). Запись разрешена для запрошенных пользователем редактора, синхронизации сателлитов и системного экспорта (REQ-028–029); без явной настройки источники только читаются. Учётные данные не должны попадать в Git или логи. Exchange: адрес явно задаёт пользователь, только HTTPS/443, без редиректов и автоматического поиска сервера. Не добавлять корпоративные адреса или реальные события в примеры и тесты.

Запуск и тесты — в README и клиентских README. Windows, физический Android и реальные учётные записи не считать проверенными по результатам сборки на Mac. Сохранять package ID `ru.ryadom.calendar` для обновления существующих установок.

Удалённый репозиторий: https://github.com/Kwentar/peklo, SSH origin `git@github.com:Kwentar/peklo.git`, ветка `main`. Пользователь разрешил публикацию после проверки (REQ-004); видимость репозитория не менять. Перед push проверять всю отправляемую историю, включая метаданные коммитов; не ограничиваться текущими файлами. В этом локальном клоне установлен непубликуемый pre-push блокировщик внутри `.git/hooks`; он не переносится при клонировании и не заменяет аудит секретов. Карточка мета-проекта имеет ключ `peklo`; локальное расположение разрешать через его настройки. Не переносить личные настройки Git и локальные пути в исходники.
